# Мини-CRM для заявок агентства

Живая версия: https://crm.201-34-137-76.sslip.io (логин и пароль в сообщении HR)
Бот: [@Jumpads_leads_bot](https://t.me/Jumpads_leads_bot)

## 1. Набросок продукта

**Проблема.** Заявки агентства приходят в разные места: бот, личные чаты менеджеров, звонки. Часть теряется, а «горячие» не видно среди остальных.

**Для кого.** Менеджер небольшого агентства, который хочет видеть все входящие лиды в одном списке и размечать их без сложной CRM.

**Как работает.**

```
Клиент -> @бот (3 вопроса: имя, контакт, запрос) ----\
Клиент -> личный Telegram менеджера (Telegram Business) --> SQLite: leads + tags --> веб-страница CRM
Менеджер -> форма «добавить лида» -------------------/                              (список, теги, фильтр)
```

Один процесс: FastAPI отдает страницу CRM, рядом в том же процессе крутится бот на aiogram. Хранилище SQLite: две таблицы, `leads` и `tags`.

**Что входит в MVP.**
1. Заявка из бота: бот задает три вопроса, контакт можно ввести текстом или отправить кнопкой. Лид сразу появляется в CRM с источником «бот» и ником в Telegram.
2. Личный Telegram (пункт 2, реализован): менеджер подключает бота к своему аккаунту через «Настройки -> Telegram для бизнеса -> Чат-боты». Входящие сообщения клиентов в личке становятся лидами с источником «личный Telegram». Повторные сообщения одного клиента дописываются в тот же лид, дублей нет. Ограничение: Telegram для бизнеса требует Premium на аккаунте менеджера.
3. Ручное добавление лида с формы.
4. Теги: добавить и снять у любого лида, клик по тегу показывает лидов с этим тегом.

**Что сознательно за скобками.** Воронка и статусы сделки, назначение ответственного, уведомления менеджеру, роли и пользователи (сейчас один общий логин), поиск, экспорт. Все это следующий шаг, MVP проверяет главное: лид не теряется и размечается.

**Почему пункт 2 через Telegram Business, а не через пользовательскую сессию (Telethon).** Сессия личного аккаунта = полный доступ ко всей переписке менеджера и риск блокировки аккаунта за автоматизацию. Business-подключение официальное, бот видит только чаты с клиентами, отключается одной кнопкой.

## 2. Разбор: как делали

**Порядок.**
1. Прочитал ТЗ и выписал обязательное ядро: пункты 1, 3, 4 должны пройти целиком «от сообщения боту до лида с тегом».
2. Написал контракт модуля в шапке `crm.py` (что на входе, что на выходе, правило «один чат = один лид»). Работаю по методологии GRACE: сначала контракт, потом код.
3. Код: хранилище, бот, веб. Один файл, около 250 строк, без фреймворка шаблонов: страница из f-строк с экранированием.
4. Тест `test_crm.py`: проходит весь путь через HTTP (ручной лид, тег, фильтр, снятие тега) плюс склейку сообщений из личного Telegram.
5. Локальный прогон с настоящим ботом: прошел анкету из своего Telegram, поставил тег, проверил фильтр.
6. Деплой в Docker на свой Ubuntu-сервер. Грабля: из docker-сети этого сервера Telegram недоступен (Network is unreachable), а с хоста доступен, поэтому контейнер работает в сети хоста.
7. Ревью кода второй моделью (OpenAI через Codex CLI). Все 10 замечаний закрыты: гонка шагов анкеты при быстрых сообщениях (изоляция событий по чату), CSRF на формах (проверка Origin), кодирование тегов в ссылках, запятая в теге, склейка лидов разных менеджеров (ключ по business_connection_id), фото с подписью вместо текста, повторный /start со старой клавиатурой, 500 на несуществующем лиде, падение бота при живом вебе (теперь процесс перезапускается). Десятое (Basic-auth по HTTP) закрыто деплоем: HTTPS через nginx и Let's Encrypt, приложение слушает только localhost.

**ИИ-инструменты.**
- Claude Code: основная разработка. Я ставил задачу и решения (стек, один процесс, Business вместо Telethon, Basic-auth, склейка лидов по чату), модель писала код и тест, я проверял результат вживую.
- Codex CLI (модель OpenAI): независимое ревью кода на баги и безопасность.

Пример постановки задачи модели:

> Мини-CRM: бот aiogram собирает имя, контакт, запрос -> лид в SQLite; страница FastAPI со списком, ручным добавлением, тегами и фильтром по тегу; один процесс; Basic-auth; пункт 2 через business_message, повторные сообщения одного клиента дописывать в тот же лид. Минимум кода, один тест на весь путь.
